## 1. What this project is

Build an evaluation system that answers: **when an NSE/BSE corporate announcement is published, can an LLM agent predict the direction/size of the price move, and does it beat trivial baselines?**

It is NOT an order-placing bot. It polls announcements, produces structured signals, sends Telegram alerts, scores each signal later against actual price moves, and stores everything so a trader app can be added later that only reads the signals.

Why: portfolio project to stand out for AI/agent/backend roles (fallback if a pure AI role is not available), plus a base for a future trader app.

- Out (v1): order placement, UI dashboard, portfolio management, derivatives, any use of non-public information.

### 2.3 Data flow
Poller -> store -> pre-filter -> analyzer -> signal saved -> Telegram (prediction) -> evaluator at each horizon -> outcome saved -> Telegram (verdict) -> scorecard/digest. Telegram is only a view.

Three timestamps per announcement: `exchange_time` (when the exchange published it), `first_seen_time` (when our poller saw it), `signal_time` (when the signal was created).

Go layout: one binary, goroutines per stage connected by channels. Packages: `poller`, `store`, `analyzer` (interface + mock + ollama + claude), `evaluator`, `notifier`, `api`.

### 2.4 Pre-announcement abnormal-move features (public data only)
- Return over previous 1, 3, 5 days minus market and sector return
- Volume and delivery-percentage spike vs 20-day average
- Price move in the hour before the announcement
- Pre-scheduled (e.g. known results date) vs surprise
- Timing bucket: market hours / pre-open / after close
- Question: if the stock already moved in the signal direction, is the remaining move smaller, or does it continue? Cause of the move is unknown; this is NOT an insider detector.

### 2.5 Success metrics
- Ingest latency: exchange_time to first_seen_time, median and p95 (no fixed target until measured)
- Coverage: % of announcements captured vs the exchange list; gaps logged
- Hit rate vs baselines per category and timing bucket
- Calibration: do higher-confidence signals have higher accuracy?
- Net return after estimated costs (brokerage, taxes, slippage)
- Priced-in test: do pre-move features improve on the LLM alone?
- Sample size (proposal): at least 300 live signals per bucket before concluding; use a statistical test
- Positive, zero, or negative edge are all valid results if measured honestly

### 2.6 Future trader-app requirements (design now, build later)
- Reads only the signals store/API; no trading code in the core
- Versioned signal schema: symbol, filing id, three timestamps, direction, confidence, horizon, category, pre-move features, model name/version, historical accuracy of that bucket
- Paper trading first; live orders only if live results justify it
- Risk controls: position size limit, daily loss limit, liquidity filter, kill switch, idempotent order ids
- Evaluation already includes costs and liquidity

### 2.7 Risks and mitigations
- LLM memorized past outcomes -> trust live data only; label history contaminated
- Unofficial exchange endpoints break or block -> cache, back off, monitor gaps, verify early with a spike
- Historical timestamps may not be true publish time -> verify; else use daily returns as the main metric
- First move happens before we can act -> evaluate timing buckets separately; focus on after-hours announcements
- Laptop downtime causes data gaps -> VPS
- LLM cost grows with volume -> two-tier models; measure one real day first

### 2.8 Milestones
M1 Spike (5 stocks; fields/timestamps understood) -> M2 Live collector (hundreds of stocks, 3 timestamps, latency logged) -> M3 Signals (mock then Ollama; Telegram predictions) -> M4 Evaluation (verdict replies, scorecard, baselines) -> M5 Claude run on live data -> M6 Pre-move model + signals API.

- Lessons: (1) for results filings the code-computed direction is exactly the "profit up -> UP" baseline, so on those filings the LLM adds nothing; its value is in non-results filings (orders, auditor resignations, MoUs) and later in features, and the scorecard must split the two; (2) good results often gap up or fall (Concord, Knack, FDC, Panth), which supports the priced-in features (D-075 item 4); (3) the 1% NEUTRAL band is rarely right on small caps: only 4 of 16 outcomes were NEUTRAL (Q-13); (4) the figure check catches real model errors and garbled scans, but cannot tell a right number on the wrong row (U-23); (5) same-company, same-exchange filings without text are scored twice (Q-16).
